# График отпусков

Внутреннее веб-приложение: сотрудники планируют отпуск на год, руководители
согласуют по цепочке. Главная ценность — выявление пересечений отпусков
у сотрудников со схожими функциями через теги с лимитом одновременного
отсутствия. Масштаб: 100–500 человек, до 5 уровней иерархии, одна компания,
один регион.

**Документация в `docs/` — источник истины.** Прочитай `docs/README.md` перед
первой задачей. При расхождении документа и кода верен документ.
Там же перечислены открытые вопросы и известные противоречия.

## Состояние проекта

В репозитории лежит работающая реализация: 343 проходящих тестов на бэкенде,
собирающийся фронтенд. **Сервер** реализует весь объём релиза 1 и большую
часть релиза 2: актуализацию графика, отгулы, внеплановые отсутствия,
доменную аутентификацию, почтовые уведомления. **Интерфейс** покрывает
сотрудника и календарь праздников; экранов администратора (загрузка
сотрудников, приглашения, теги, настройки) и руководителя (согласование,
сводный календарь команды) нет. Это релиз 1.1, план —
`docs/07-mvp-scope.md`, разделы 3–8. Есть демо-режим с вымышленной
компанией в отдельной базе.

Не называй функцию готовой, пока у неё нет экрана: сотрудник и руководитель
работают только через интерфейс.

Чего нет: линтеров и непрерывной интеграции, манифестов Kubernetes,
инструкции по развёртыванию на Railway.
Это итерации 2 и 3 в `docs/tasks/00-skeleton.md`. Поддерживаются три способа
развёртывания — Docker, Kubernetes, Railway — из одних и тех же образов.
Запуск через Docker и `docker compose` уже работает — см. `README.md`.

Не сделано по функциональности: экспорт графика, сверхурочные часы,
мобильное приложение. Загрузка графика отпусков из CSV — в долгосрочном
бэклоге, не планируется.

## Архитектура и стек

API-first модульный монолит: тонкий SPA-клиент, единый REST API, один серверный
процесс с модулями по границам предметной области, одна база данных.
Обоснование и отвергнутые альтернативы — `docs/01-adr-001-architecture.md`.

Django + DRF, React + TypeScript (Vite), PostgreSQL, Docker —
`docs/02-adr-002-stack.md`. Библиотеки за пределами ADR-002 не добавлять
без вопроса; уже согласованные исключения перечислены в `backend/requirements.txt`.

Приложения бэкенда:

| Приложение | Содержание |
|---|---|
| `employees` | Сотрудники, оргструктура, теги и лимиты, импорт кадровой выгрузки |
| `company` | Календарь праздников, справочники, настройки, брендирование |
| `schedule` | График, правила проверки, регистры, согласование, уведомления в ленте |
| `audit` | Журнал изменений |
| `sso` | Доменная аутентификация: Kerberos и Keycloak |
| `mailer` | Очередь почтовых уведомлений |
| `demo` | Демо-режим: отдельная база, вход по роли, загрузка демо-данных (`docs/15-demo-mode.md`) |

## Ключевые принципы реализации

Нарушение любого из них — повод остановиться и спросить, а не обойти.

- **Бизнес-логика живёт на сервере в единственном экземпляре.** Фронтенд
  не повторяет расчёты, а вызывает серверную проверку (`/schedule-entries/validate/`) —
  ту же, что срабатывает при сохранении.
- **Пороговые значения — данные, а не код.** Нормы 28, 14 и 7 дней, длина
  рабочего дня, число уровней согласования лежат в справочниках и настройках.
  Изменение нормы должно быть настройкой администратора, а не правкой кода.
- **Баланс не хранится, а вычисляется** суммой регистра начислений и списаний.
  Отдельное поле с итогом рассинхронизируется с историей.
- **Видимость данных определяется на сервере** в каждом эндпоинте, клиент
  никогда не полагается на собственную фильтрацию.
- **Демо-данные живут в отдельной базе** (`demo`). Демо-запрос подменяет
  соединение `default` на время запроса (`demo/db.py`), поэтому код
  не хранит соединение в переменных модуля и не обращается к базе `demo`
  по имени — иначе демо и рабочие данные смешаются.
- **Аудит пишется сигналами моделей**, а не вызовами по коду: иначе новое
  место изменения данных окажется незалогированным незаметно.
- **Контракт API зафиксирован тестами** в `schedule/tests_contract.py` —
  они сверяют состав полей с типами фронтенда в `frontend/src/types.ts`.
  Переименовал поле — упадёт тест, а не браузер пользователя.

## Правила работы

- Ветки `feature/*`, всё через Pull Request в `main`; прямых коммитов в `main` нет.
- Коммиты `тип: описание на русском` (`feat:`, `fix:`, `docs:`, `test:`,
  `chore:`, `refactor:`). В теле — зачем, а не что: что видно из diff.
  Коммиты небольшие, по одному изменению.
- PR описывается для не-разработчика: что сделано, как проверить, какие
  решения приняты и почему.
- **Не добавляй функциональность за пределами текущего задания.** Если задача
  кажется неполной без соседней — спроси, не делай.
- **При противоречии в документах или неясности — остановись и спроси.**
  Расхождения в комплекте уже находили, они перечислены в `docs/README.md`.
- Секреты не коммитить; все настройки через переменные окружения, образец
  в `.env.example`.
- Документация обновляется вместе с кодом: меняешь поведение — правь документ
  в том же PR.
