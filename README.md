# График отпусков

Веб-приложение для планирования и согласования отпусков. Сотрудники вносят
график на год, руководители согласуют по цепочке, система проверяет нормы
и предупреждает о пересечениях отпусков у сотрудников со схожими функциями.

Рассчитано на 100–500 человек и до 5 уровней иерархии.

---

## Что умеет

**Планирование.** Годовой календарь на одном экране, выделение периода мышью,
проверка до сохранения. Накопленные дни рассчитываются на любую дату,
праздники не списываются с баланса и продлевают отпуск, отпуск на стыке лет
делится по годам для годовой нормы и остаётся непрерывным для правила о двух
неделях.

**Проверки.** Годовая норма, непрерывный отпуск, длительный отпуск, потолок
доступных дней, захват выходных, лимиты одновременного отсутствия по тегам.
Пороговые значения — данные, а не константы в коде: норма 28 дней меняется
настройкой, без правки программы. Экран настроек — в релизе 1.2.

**Теги и пересечения.** Сотруднику назначаются теги — автоматически
по оргструктуре и вручную. По каждому тегу задаётся лимит одновременного
отсутствия. Сотрудник видит в календаре дни, где лимит по его тегам
исчерпан. Администратор задаёт лимиты и назначает теги на экране «Теги»,
руководитель видит пересечения в сводном календаре команды с фильтром по тегу.

**Согласование.** Цепочка до четырёх уровней оргструктуры, строго
последовательно. Подтверждение исключений с обязательным комментарием,
отклонение на любом уровне, отзыв графика. Актуализация утверждённого
графика согласуется двумя уровнями выше; отказ возвращает ровно то,
что было утверждено. Руководитель принимает решения на экране «Требует
решения»: графики, где очередь дошла до него, и запросы исключений
со сработавшими правилами и списком пересечений.

**Учёт рабочего времени.** Отгулы за работу в выходные дни (баланс в часах,
отгул берётся целым днём), внеплановые отсутствия с отдельным счётчиком
в разрезе причин. Работает на сервере, экраны — в релизе 1.2.

**Администрирование.** Календарь праздников с загрузкой и переносом года.
Импорт сотрудников и оргструктуры из CSV транзакцией с предпросмотром
написан на сервере, экран загрузки и выдача ссылок-приглашений — в релизе 1.1.

**Инфраструктура.** Журнал изменений пишется автоматически (экран просмотра —
в релизе 1.2), доменная аутентификация через Kerberos и Keycloak, почтовые
уведомления с очередью.

**Демо-режим.** Кнопка на экране входа открывает вымышленную компанию
с готовым графиком — без кадровой выгрузки, настройки и пароля.

Не реализовано: экспорт графика, сверхурочные часы, мобильное приложение.

## Запуск через Docker

Нужен Docker с плагином Compose.

```bash
git clone https://github.com/DGordeenko/vacation-planner.git
cd vacation-planner
cp .env.example .env
docker compose up --build
```

Поднимутся три сервиса: PostgreSQL, бэкенд и фронтенд. Миграции применяются
автоматически при старте.

Приложение — **http://localhost:8080**

Проверить живость:

```bash
curl http://localhost:8080/api/health/
# {"status":"ok","database":"ok"}
```

### Первый администратор

Чтобы войти в чистую систему без демонстрационных данных, задайте в `.env`
`ADMIN_EMAIL` и `ADMIN_PASSWORD` до первого запуска — администратор создастся
при старте контейнера. Повторные запуски его не меняют. Подробно —
[`docs/14-initial-admin.md`](docs/14-initial-admin.md).

### Демо-режим

На экране входа есть кнопка **«Демо-режим»**: вымышленная компания
на 157 человек с готовым графиком на следующий год, вход выбором роли —
сотрудник, руководитель или администратор, без пароля. Демо-данные лежат
в отдельной базе и рабочих не касаются, при каждом старте контейнера
загружаются заново.

По умолчанию выключено, включается только явно: `DEMO_MODE_ENABLED=True`
в `.env` или в переменных площадки. Сбой подготовки демо не мешает запуску
рабочей системы — пропадает только кнопка. Подробно —
[`docs/15-demo-mode.md`](docs/15-demo-mode.md).

### Тестовые учётные записи в рабочей базе

Для разработки, когда нужны данные в основной базе, а не в демо:

```bash
docker compose exec backend python manage.py seed_demo
```

Создаёт оргструктуру, календарь праздников на 2027 год, теги с лимитами
и учётные записи (пароль `demo12345`):

| Роль | Почта |
|---|---|
| Сотрудник | `user1@demo.ru` |
| Руководитель | `manager@demo.ru` |
| Администратор | `admin@demo.ru` |

Остальные сотрудники создаются с приглашениями, без пароля.

### Остановка

```bash
docker compose down          # остановить
docker compose down -v       # остановить и удалить базу
```

## Запуск для разработки

Бэкенд и фронтенд запускаются отдельно, база — SQLite, если не задан
`DATABASE_URL`.

```bash
# Бэкенд
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo
python manage.py runserver        # http://localhost:8000
```

```bash
# Фронтенд, в отдельном терминале
cd frontend
npm install
npm run dev                       # http://localhost:5173
```

Запросы к `/api` проксируются на бэкенд настройкой в `vite.config.ts`.

### Тесты и линтеры

```bash
cd backend && pip install -r requirements-dev.txt
cd backend && ruff check . && python manage.py test        # 437 тестов
cd frontend && npm run lint && npx tsc -b && npm run build
```

То же выполняет CI на каждый PR.

## Настройка

Все параметры задаются переменными окружения, образец — `.env.example`.
Секретов в репозитории нет.

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | Ключ Django. Обязательно заменить в продакшене |
| `DEBUG` | По умолчанию `False` |
| `ALLOWED_HOSTS` | Домены через запятую |
| `DATABASE_URL` | `postgres://...`; без неё используется SQLite |
| `PORT` | Порт сервиса |
| `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` | Нужны, только если фронтенд на другом домене |
| `VITE_API_BASE_URL` | Адрес API. Пусто — относительный путь через прокси nginx |
| `RUN_MIGRATIONS` | `0` отключает миграции при старте контейнера |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Первый администратор, создаётся при старте, если его ещё нет. Подробно — `docs/14-initial-admin.md` |
| `ADMIN_FULL_NAME`, `ADMIN_EMPLOYEE_NUMBER`, `ADMIN_HIRE_DATE` | Необязательные поля администратора, есть значения по умолчанию |
| `DEMO_MODE_ENABLED` | Кнопка «Демо-режим» на экране входа. По умолчанию выключено |
| `DEMO_DATABASE_URL`, `DEMO_LOAD_ON_START` | Отдельная база демо (по умолчанию SQLite в контейнере) и загрузка при старте. Подробно — `docs/15-demo-mode.md` |

Доменная аутентификация — `docs/11-sso-setup.md`,
почтовые уведомления — `docs/12-mail-setup.md`.

### Размещение на других площадках

Образы переносимые: порт и настройки берутся только из переменных окружения.

**Kubernetes.** Манифесты — `deploy/k8s/` (`kubectl apply -k deploy/k8s`):
миграции отдельным Job, почта — CronJob, пробы на `/api/health/`. Пошагово —
`docs/18-deploy-kubernetes.md`.

**Railway.** По сервису на папку, PostgreSQL плагином (даёт `DATABASE_URL`).
Поскольку сервисы получают разные домены, задать `VITE_API_BASE_URL`
с адресом бэкенда и перечислить домен фронтенда в `CORS_ALLOWED_ORIGINS`
и `CSRF_TRUSTED_ORIGINS`.

Манифесты и инструкции — в работе, см. `docs/tasks/00-skeleton.md`.

## Состояние

Сервер реализует весь объём релиза 1 и большую часть релиза 2. В интерфейсе
есть экраны сотрудника, руководителя (решения по графикам и исключениям,
календарь команды) и администратора для тегов и праздников. Экранов загрузки
сотрудников, приглашений и настроек пока нет. Подробная таблица — `docs/07-mvp-scope.md`, раздел 3.

Остаток релиза 1.1 «Запуск MVP»: загрузка сотрудников, ссылки-приглашения,
резервное копирование и проверка запуска на Railway. Затем релиз 1.2:
экраны учёта времени и настроек, CI, манифесты Kubernetes. План —
`docs/07-mvp-scope.md`, разделы 5–8.
