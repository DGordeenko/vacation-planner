# Структура API
## Приложение для сбора данных и подготовки графика отпусков

> Часть комплекта проектной документации. Обзор и порядок чтения — в `README.md`.


**Связано с:** ФЗ, ADR-001 (архитектура), ADR-002 (стек), Модель данных

REST API на Django REST Framework, разбит по тем же модулям, что и остальные документы.

---

## 0. Общие принципы

- **Базовый путь:** `/api/v1/` — версионирование через префикс пути, чтобы можно было позже ввести `/api/v2/` без ломки текущих клиентов (веб и будущее мобильное приложение).
- **Аутентификация:** в MVP — токен или сессия после логина по email/паролю (`/api/v1/auth/`). Заложено так, чтобы позже добавить доменную аутентификацию (SSO), не меняя остальные эндпоинты — авторизация всегда сверяется по одному и тому же признаку «текущий пользователь», независимо от способа входа.
- **Формат данных:** JSON, даты — `YYYY-MM-DD`, дата-время — ISO 8601.
- **Ошибки параметров:** неверный год, дата или идентификатор в запросе — 400 с полем, а не 500.
- **Пагинация списков:** параметры `page`, `page_size` (по умолчанию 50, не больше 500), ответ содержит `count`, `next`, `previous`, `results`.
- **Фильтрация списков:** через query-параметры (`?employee_id=...&date_from=...&date_to=...`).
- **Формат ошибок:** единый вид `{ "detail": "человеко-читаемое сообщение", "code": "machine_readable_code" }`; ошибки валидации — `{ "errors": { "поле": ["сообщение"] } }`.
- **Видимость данных:** для списков сотрудников/графика сервер сам ограничивает выдачу по правилу «сотрудник видит только себя, руководитель — себя и всю оргструктуру под собой, администратор — всех» — фильтрация происходит на бэкенде, а не на клиенте.

## 1. Аутентификация

| Метод | Путь | Описание | Доступ |
|---|---|---|---|
| POST | `/api/v1/auth/register/` | Регистрация пользователя (MVP) | Публично |

| POST | `/api/v1/auth/accept-invitation/` | Вход по ссылке-приглашению: `invitation_token`, `password`. | POST | `/api/v1/auth/logout/` | Выход | Аутентифицирован |

| POST | `/api/v1/auth/demo-login/` | Вход в демо-режим выбором роли, без пароля. Токен со схемой `Demo` работает только с демо-базой (`15-demo-mode.md`) | Публично, при включённом демо |

## 11. Принятые решения

1. Версионирование через префикс пути (`/api/v1/`) — простой и явный способ вносить несовместимые изменения в будущем, не ломая текущих клиентов.
2. Все проверки видимости данных (кто кого видит по иерархии) реализуются на сервере в каждом эндпоинте списка/карточки — клиент никогда не полагается на собственную фильтрацию.
3. Загрузка CSV (сотрудники, календарь) — отдельные POST-эндпоинты с суффиксом `import-csv`, использующие ту же логику валидации, что и обычные создание/обновление через API — гарантирует одинаковое поведение независимо от способа ввода данных.
4. Действия, не являющиеся простым CRUD (подтверждение исключения, согласование шага, подтверждение сдвига дат), вынесены как отдельные под-пути (`/…/approve/`, `/…/confirm-holiday-extension/`) — стандартная практика DRF для нестандартных операций над ресурсом.
5. Эндпоинт `/schedule-entries/validate/` выполняет те же проверки, что и сохранение, но без записи в базу — позволяет интерфейсу предупреждать пользователя заранее, а не после отказа в сохранении. Логика проверок при этом одна и та же (единая точка правды), продублированной валидации на клиенте нет.
6. Проверка годовой нормы (правило «не менее 28 дней») вынесена в отдельный эндпоинт отправки года на согласование, а не выполняется при сохранении отдельной записи — иначе внести первую запись графика было бы невозможно.
7. Пороговые значения правил читаются клиентом через `/validation-rules/` и не зашиваются в код интерфейса — при изменении нормы администратором интерфейс автоматически показывает актуальные значения.

## 12. Вне рамок этого документа

- Точные схемы тела запроса/ответа (JSON Schema) по каждому эндпоинту — прорабатываются при реализации.
- Ограничение частоты запросов (rate limiting).
