# Проектирование интерфейса и брендирование

**Связано с:** ФЗ, Структура API, ADR-002 (стек)

---

## 1. Принципы, положенные в основу

1. **Календарь — главный экран, а не форма.** Планирование отпуска — задача пространственная: человек думает «хочу две недели в июле», а не «date_from = 2027-07-06». Основной способ ввода — выделение диапазона прямо на календаре, форма с полями — вспомогательный.
2. **Проверки предупреждают, а не наказывают.** Правила показываются **до** сохранения (эндпоинт предварительной проверки), в момент выделения дат. Блокировка после нажатия «Сохранить» — худший сценарий: пользователь уже принял решение и получает отказ.
3. **Блокировка всегда объясняет и предлагает выход.** Сообщение содержит: какое правило нарушено, конкретные цифры («запланировано 21 день из 28»), и кнопку «Запросить подтверждение у руководителя» — блокировка не должна быть тупиком.
4. **Разделение «мои дела» и «данные».** Руководитель заходит в систему не смотреть календарь, а закрывать задачи. Поэтому лента «Требует моего решения» — отдельная точка входа с числовым счётчиком, а не пункт в глубине меню.
5. **Плотность информации выше декоративности.** Это внутренний рабочий инструмент, которым пользуются регулярно и быстро. Приоритет — видеть много данных сразу, без лишних отступов и анимаций.
6. **Доступность как требование, а не пожелание.** Контраст текста не ниже WCAG AA, полная навигация с клавиатуры, статусы никогда не кодируются **только** цветом — всегда дублируются текстом или иконкой (иначе система нечитаема для людей с нарушением цветовосприятия, а таких около 8% мужчин).

## 2. Ключевые экраны

### 2.1. Мой график (главный экран сотрудника)

**Основная область:** годовой календарь — 12 месяцев на одном экране, компактной сеткой. Год виден целиком, потому что планирование отпуска — годовая задача.

Обозначения дней: отпуск, внеплановое отсутствие, РВД, сверхурочные, праздники, выходные. Каждый тип — свой цвет **и** своя штриховка/иконка.

**Боковая панель (постоянно видна):**
- Баланс дней на сегодня и на конец года (прогноз);
- Прогресс годовой нормы: «Запланировано 21 из 28 дней» с полосой заполнения;
- Индикатор непрерывного отпуска: «Максимальный непрерывный: 10 дней (требуется 14)»;
- Счётчик внеплановых отсутствий за год.

Эти три показателя — ровно те, по которым сотрудника заблокируют при отправке графика. Показывать их постоянно, а не в момент отказа.

**Ввод:** выделение диапазона мышью → всплывающая карточка с выбором типа записи → мгновенный результат предварительной проверки внутри карточки → сохранение.

### 2.2. Карточка внесения записи

Компактная карточка, а не полноэкранная форма. Состав меняется по типу записи:
- **Отпуск:** даты, расчёт («14 календарных, 11 отпускных дней, списывается 11»), блок продления на праздники с явной кнопкой подтверждения новой даты.
- **Внеплановое отсутствие:** даты, причина из списка, поле свободного текста при выборе «Другое».
- **РВД:** дата, ссылка на задачу, вид компенсации (если учёт включён).
- **Сверхурочные:** дата, ссылка на задачу, количество часов.

Результаты проверок отображаются **внутри карточки в реальном времени** по мере изменения дат, а не после отправки.

### 2.3. Календарь команды (руководитель)

Диаграмма Ганта: строки — сотрудники, колонки — дни/недели года, полосы — отпуска. Формат выбран потому, что главная задача руководителя — увидеть **пересечения**, а они видны только при вертикальном сопоставлении.

**Фильтр по тегу** — ключевой элемент: выбор тега оставляет только сотрудников с ним и подсвечивает даты, где достигнут лимит одновременного отсутствия. Именно это решает исходную задачу выявления пересечений у сотрудников со схожими функциями.

**Своя структура / все подразделения.** По умолчанию руководитель видит график своей ветки. Переключатель «Все подразделения» показывает планируемый график всей компании — отпуска на согласовании и утверждённые; черновики чужих подразделений не показываются.

**Кто решает.** Подсказка у неутверждённого отпуска называет, чьего решения он ждёт. По нажатию открывается карточка: период, статус, цепочка согласования (✓ — согласовал, выделен текущий шаг, остальные ждут очереди) или руководитель, которому ушёл запрос исключения.

Дополнительно: фильтр по оргединице, переключение периода (год/квартал/месяц), режим «только конфликты».

### 2.4. Требует моего решения (руководитель)

Единый список задач руководителя со счётчиком в шапке приложения. Типы элементов: запросы подтверждения исключений, графики на согласование, изменения утверждённых графиков.

Каждый элемент показывает достаточно контекста для решения без перехода на другой экран: кто, какой период, какое правило нарушено, текущая загрузка команды в эти даты. Действия — «Согласовать» / «Отклонить» с полем комментария (обязательным при отклонении и при подтверждении исключения).

### 2.5. Администрирование

Раздел со справочниками: сотрудники (+ загрузка CSV), оргструктура, теги и лимиты, календарь праздников (+ загрузка CSV), причины отсутствия, правила проверок с порогами, настройки бренда.

Экран загрузки CSV: выбор файла → **предпросмотр с построчной валидацией** → подтверждение. Загрузка выполняется целиком или не выполняется вовсе, поэтому пользователь должен увидеть все проблемы до применения.

Часть этих экранов может быть закрыта встроенной админ-панелью Django (см. ADR-002) — это экономит время разработки на редко используемых справочниках.

### 2.6. Навигация и уведомления

- **Шапка:** «Мой график», «Отгулы» — всем; «Требует решения», «Команда», «Теги» —
  руководителям; «Управление» — администратору. Внутри «Управления» — подменю:
  сотрудники и приглашения, РВД, праздники, журнал, настройки. Так шапка
  не переносится на вторую строку при любом наборе прав.
- **Раздел — в адресе** (`#team`, `#settings`): обновление страницы и «Назад»
  браузера возвращают в тот же раздел. Раздел, недоступный по правам, открывает
  «Мой график».
- **Уведомления — колокольчик** со счётчиком непрочитанных (считает сервер, по всем,
  а не по загруженной странице). Список последних; нажатие отмечает прочитанным
  и ведёт к действию: запрос на решение — в «Требует решения», остальное —
  к своему графику. «Прочитать все».
- **Телефон (до 720 px):** название и колокольчик в одной строке, разделы —
  прокручиваемой строкой; широкие таблицы прокручиваются внутри карточки,
  страница по горизонтали не сдвигается.

## 3. Брендирование под компанию

### 3.1. Подход

Все визуальные значения выносятся в **семантические CSS-переменные**. Компоненты интерфейса никогда не содержат цвет напрямую — только ссылку на переменную.

Бренд задаётся **минимальным набором базовых значений**, из которых остальная палитра выводится автоматически:

| Переменная | Назначение |
|---|---|
| `--brand-primary` | Основной цвет бренда (кнопки, акценты, активные состояния) |
| `--brand-contrast` | Цвет текста на основном цвете (рассчитывается или задаётся явно) |
| `--brand-radius` | Радиус скругления элементов (влияет на «характер» интерфейса) |
| `--brand-font` | Основная гарнитура |

Производные оттенки (наведение, нажатие, фон-подложка, границы) вычисляются от `--brand-primary` функцией `color-mix()` — это исключает необходимость просить у компании 20 значений цвета вместо одного.

Такой подход выбран сознательно вместо полноценной системы дизайн-токенов с генерацией под несколько платформ: для одного продукта одной команды это избыточно, а CSS-переменных достаточно.

### 3.2. Логотип и идентификация

- Логотип загружается администратором (SVG или PNG), отображается в шапке приложения и на экране входа.
- Отдельно — иконка приложения (favicon).
- Название организации — текстовое поле, используется в заголовке и в будущих экспортируемых документах.

### 3.3. Настройки бренда

Хранятся в базе данных (расширение `CompanySettings`), а не в конфигурационных файлах — чтобы администратор менял их через интерфейс без участия разработчика и без переразвёртывания приложения.

| Поле | Тип | Описание |
|---|---|---|
| brand_primary_color | string | Основной цвет (HEX) |
| brand_contrast_color | string, nullable | Цвет текста на основном (null = рассчитывается автоматически) |
| brand_radius | string | Радиус скругления |
| brand_font_family | string | Гарнитура |
| brand_logo | file | Логотип |
| brand_favicon | file | Иконка приложения |
| organization_name | string | Название организации |

Соответствующий эндпоинт: `GET/PATCH /api/v1/settings/branding/` (чтение — для всех аутентифицированных, изменение — администратор).

### 3.4. Обязательная проверка контраста

При сохранении цвета бренда система **проверяет контрастность** пары «основной цвет / контрастный цвет» по стандарту WCAG AA (коэффициент не ниже 4.5:1 для обычного текста).

При недостаточном контрасте администратору показывается предупреждение с предложением автоматически подобранного контрастного цвета. Без этой проверки любой светлый корпоративный цвет сделает текст на кнопках нечитаемым — это самая частая проблема кастомизируемых интерфейсов.

### 3.5. Тёмная тема

Поскольку все цвета уже вынесены в переменные, поддержка тёмной темы достигается вторым набором значений тех же переменных. Реализация — по желанию, но структура интерфейса закладывается так, чтобы её добавление не требовало правки компонентов.

## 4. Технические решения по интерфейсу

| Решение | Обоснование |
|---|---|
| Компоненты не содержат жёстко заданных цветов — только CSS-переменные | Единственный способ обеспечить брендирование и тёмную тему без переписывания интерфейса |
| Пороговые значения правил (28/14/7) не зашиваются в интерфейс, а читаются из API | При изменении нормы администратором интерфейс покажет актуальные значения без доработки |
| Логика проверок не дублируется на клиенте — используется серверная предварительная проверка | Исключает расхождение между тем, что показал интерфейс, и тем, что решил сервер |
| Адаптивная вёрстка закладывается сразу, хотя мобильная версия не в MVP | Годовой календарь и диаграмма Ганта — самые сложные для адаптации элементы; заложить сетку заранее дешевле, чем переделывать |
| Все статусы дублируются текстом/иконкой помимо цвета | Доступность + корректная работа при любом бренде: на нестандартной палитре различение «только цветом» ломается |

---

**Браузеры.** Поддерживаются актуальные Chrome, Edge, Firefox и Safari (macOS, iOS) —
Safari не старше 15. Сборка Vite нацелена на Safari 14+. Чего в стилях и коде
избегаем ради Safari: `color-mix()` (Safari 16.2+), запись в буфер обмена после
ожидания ответа сервера (Safari разрешает её только в обработчике нажатия —
используется `ClipboardItem` с обещанием), системный вид выпадающих списков
(`appearance: none` с своей стрелкой). Проверка — прогон сценариев всех ролей
в движке WebKit (WebKitGTK через WebDriver) на ширине компьютера и телефона.

## 5. Вне рамок этого документа

- Детальная проработка макетов (визуальный дизайн, точные размеры, иконки).
- Выбор конкретной библиотеки компонентов интерфейса — определяется на старте разработки; критерий выбора: поддержка стилизации через CSS-переменные и доступность из коробки.
