# Отчёт о проверке комплекта документов

**Проверены:** ФЗ, ADR-001 (архитектура), ADR-002 (стек), Модель данных, Структура API
**Критерии:** согласованность между документами, полнота учёта требований, гибкость и готовность к изменению требований

---

## 1. Найденные расхождения между документами (исправлены)

| № | Расхождение | Последствие, если бы не исправили | Исправление |
|---|---|---|---|
| 1 | В ФЗ CSV-поле табельного номера называлось `employee_id`, в модели данных `id` — это внутренний UUID, а табельный номер — `employee_number` | Прямая ошибка при реализации загрузки CSV: файл ссылался бы на несуществующее поле | В ФЗ переименовано в `employee_number` / `manager_employee_number`, добавлено примечание о разделении бизнес-ключа и внутреннего идентификатора |
| 2 | В ФЗ CSV графика содержал объединённое поле `reason_or_task_link`, в модели данных причина и ссылка на задачу — разные поля с разными типами | Неоднозначная валидация при загрузке; невозможность отличить причину от URL | Формат CSV в ФЗ приведён к структуре хранения: `reason_code`, `custom_reason_text`, `task_link` разделены |
| 3 | ADR-001 перечислял модули «Пользователи, Отпуска, Календарь, Теги», тогда как модель данных содержит также аудит, а требования — уведомления | Модули аудита и уведомлений оказались бы «ничьими» при разработке | Список модулей в ADR-001 приведён в соответствие с моделью данных |

## 2. Пробелы в покрытии требований (устранены)

| № | Требование из ФЗ | Чего не хватало | Исправление |
|---|---|---|---|
| 1 | «Аларм руководителю» — фигурирует в правилах и в лимитах по тегам | Механизм доставки алармов не был описан **ни в одном** документе: не было ни сущности уведомления, ни эндпоинта | Добавлен раздел 4.9 ФЗ (уведомления), сущность `Notification` в модели данных, раздел 8 в API |
| 2 | Учёт компенсации РВД (отгул/оплата) как опциональная фича на уровне системы **и** подразделения/сотрудника | В модели был только глобальный флаг; сам вид компенсации негде было хранить | Добавлено поле `rvd_compensation_type` в `ScheduleEntry` и переопределения на уровне `OrgUnit` и `Employee` |
| 3 | Просмотр графика всех сотрудников с одинаковым тегом (исходная цель — выявление пересечений) | В API был только счётчик числа отпускников по тегу, но не сам календарь | Добавлен фильтр `tag_id` в списке записей графика, требование явно зафиксировано в ФЗ |
| 4 | Внеплановое отсутствие «учитывается отдельным счётчиком» | Счётчик нигде не был доступен для просмотра | Добавлен эндпоинт годовой сводки `annual-summary`, требование уточнено в ФЗ |
| 5 | Экспорт графика (заглушка) | Заглушки не было даже в API | Добавлен раздел 9 в API |
| 6 | Правило «не менее 28 дней в году» | Не было определено, за какой год и в какой момент проверяется. При проверке на каждой записи внести первую запись графика было бы невозможно | Уточнено в ФЗ: проверка календарного года при отправке годового графика; добавлен эндпоинт `submit-year` |

## 3. Логические неоднозначности (устранены)

| № | Проблема | Исправление |
|---|---|---|
| 1 | Правила 7 и 8 не покрывали промежуточные случаи: отпуск со вторника по четверг не является блоком «Пн-Пт», но и не захватывает выходные — поведение системы было неопределённым | Правило 8 переформулировано обобщённо: блокируется любой отпуск, не захватывающий ни одного выходного дня. Обобщение помечено как требующее подтверждения на приёмке |
| 2 | В модели данных `Employee.manager_employee_id` дублировал `OrgUnit.manager_id` («кэш») | Поле удалено: руководитель определяется через оргединицу. Дублирование при строгом дереве создавало риск рассинхронизации при переводах сотрудников |

## 4. Гибкость и готовность к изменению требований

### Что усилено

| № | Риск | Решение |
|---|---|---|
| 1 | Пороговые значения правил (28, 14, 7 дней) были зашиты в перечисление `rule_violated` и подразумевали код. Изменение «сделать 30 дней вместо 28» требовало бы доработки и миграции базы | Введён справочник `ValidationRule`: код правила, порог, признак включённости, кто подтверждает исключение. Изменение порога и отключение правила стали **настройкой**, а не доработкой |
| 2 | Клиентский интерфейс мог бы зашить те же значения у себя, и они разошлись бы с сервером | Пороги читаются интерфейсом через `/validation-rules/`; добавлен эндпоинт `/schedule-entries/validate/`, выполняющий ровно ту же серверную проверку без сохранения — дублирующей логики на клиенте нет |
| 3 | Норма отпуска задана глобально. При появлении категорий с увеличенной нормой (дополнительный отпуск за особые условия) потребовалась бы переделка | Заложено поле индивидуального переопределения нормы (в MVP не используется), риск зафиксирован в открытых вопросах ФЗ |
| 4 | Опциональные настройки не имели механизма исключений для отдельных подразделений | Введён принцип наследования «система → оргединица → сотрудник» с приоритетом более частного уровня |

### Что оценено как достаточное без изменений

- **Готовность к мобильному приложению** — обеспечена архитектурно: единый REST API, отсутствие серверного рендеринга, вся логика видимости данных и проверок на сервере. Мобильный клиент не потребует изменений бэкенда.
- **Переход на доменную аутентификацию** — заложен: авторизация во всех эндпоинтах опирается на понятие «текущий пользователь» независимо от способа входа; добавление SSO затрагивает только модуль аутентификации.
- **Интеграция с матрицей компетенций** — теги вынесены в отдельную сущность с полем источника назначения (`auto_org` / `manual`), поэтому добавление третьего источника (`competency_matrix`) не потребует изменения структуры.
- **Версионирование API** (`/api/v1/`) — позволяет вносить несовместимые изменения, не ломая существующих клиентов.
- **Вынос модулей в отдельные сервисы** — возможен благодаря модульным границам, зафиксированным в ADR-001.

## 5. Оставшиеся риски (не устраняются на этом этапе, требуют вашего решения)

| № | Риск | Комментарий |
|---|---|---|
| 1 | `CompanySettings` не версионируется во времени | Если норма отпуска изменится с определённой даты, история прошлых лет пересчитается по новому значению. Для MVP приемлемо; при необходимости потребуется история значений настроек |
| 2 | Обобщение правила о захвате выходных | Требует подтверждения, что соответствует исходному намерению (см. открытый вопрос 4 в ФЗ) |
| 3 | Эскалация согласования для верхних уровней оргструктуры | Принято предположение об утверждении администратором; требует подтверждения (открытый вопрос 1 в ФЗ) |
| 4 | Канал уведомлений в MVP — только лента в интерфейсе | Если руководители не заходят в систему регулярно, алармы могут оставаться незамеченными. Почтовые уведомления архитектурно возможны, но вынесены за рамки MVP |
| 5 | Одновременное редактирование графика несколькими руководителями | Поведение при конфликте правок не определено; для MVP с небольшим числом пользователей риск низкий |
