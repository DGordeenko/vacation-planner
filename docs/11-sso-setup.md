# Настройка доменной аутентификации

Поддерживаются два способа. Kerberos — основной: пользователь в домене
входит без ввода пароля. Keycloak по OpenID Connect — альтернативный,
работает и вне домена.

Оба включаются независимо и могут работать одновременно: экран входа
покажет только настроенные способы.

---

## 1. Общие правила допуска

Провайдер отвечает только на вопрос «кто это». Решение о допуске
принимается одинаково для обоих способов:

1. Из домена берётся почтовый адрес (`userPrincipalName`).
2. По нему ищется сотрудник в системе.
3. Если сотрудника нет — **вход запрещается**. Сотрудники заводятся
   только загрузкой кадровой выгрузки: доменная аутентификация
   подтверждает личность, но не даёт права на существование в системе.
   Автосоздание завело бы людей без оргструктуры, то есть без
   руководителя и без согласующего график.
4. Если сотрудник отмечен как уволенный — вход запрещается.
5. При первом доменном входе снимается признак приглашения.

Роли и права берутся из справочника сотрудников, а не из домена:
оргструктура ведётся в системе.

## 2. Kerberos (SPNEGO)

### 2.1. Требования к серверу

```bash
apt install libkrb5-dev krb5-user
pip install gssapi
```

Без пакета `gssapi` приложение запускается и работает по паролю,
а доменный вход возвращает понятную ошибку конфигурации.

### 2.2. Служебный принципал и keytab

В домене создаётся служебная учётная запись и принципал вида
`HTTP/<полное-имя-сервера>@<REALM>`, например
`HTTP/vacation.corp.ru@CORP.LOCAL`.

Keytab выгружается на сервер и закрывается от посторонних:

```bash
chown app:app /etc/vacation.keytab
chmod 400 /etc/vacation.keytab
```

### 2.3. Настройки приложения

```python
SSO_KERBEROS = {
    "enabled": True,
    "keytab": "/etc/vacation.keytab",
    # Realm в AD и почтовый домен часто различаются.
    "realm_to_email_domain": {"CORP.LOCAL": "corp.ru"},
    "email_domain": "corp.ru",   # запасной вариант для принципалов без realm
}
```

### 2.4. Как это выглядит

1. Браузер обращается к `/api/v1/auth/negotiate/`.
2. Сервер отвечает `401` с заголовком `WWW-Authenticate: Negotiate` —
   это штатная часть протокола, а не ошибка.
3. Браузер повторяет запрос с билетом.
4. Сервер проверяет билет по keytab и выдаёт токен приложения.

### 2.5. Настройка браузеров

Chrome и Edge передают билет только доверенным адресам. Через групповые
политики задаётся `AuthServerAllowlist` со значением вида `*.corp.ru`.
Firefox — параметр `network.negotiate-auth.trusted-uris`.

Без этой настройки браузер не приложит билет, и вход завершится
приглашением ввести пароль.

### 2.6. Обратный прокси

Заголовок `Authorization` должен доходить до приложения. Nginx по
умолчанию его передаёт, но при наличии собственной аутентификации
на прокси её нужно отключить для `/api/v1/auth/negotiate/`.

## 3. Keycloak (OpenID Connect)

### 3.1. Настройка в Keycloak

В realm создаётся клиент:

| Параметр | Значение |
|---|---|
| Client ID | `vacation-app` |
| Client authentication | включено (confidential) |
| Standard flow | включён |
| Valid redirect URIs | `https://vacation.corp.ru/auth/callback` |
| Web origins | `https://vacation.corp.ru` |

В токен обязательно должен попадать почтовый адрес: в маппере клиента
включается claim `email`. Без него сопоставление невозможно, и вход
вернёт ошибку `email_claim_missing`.

### 3.2. Настройки приложения

```python
SSO_OIDC = {
    "enabled": True,
    "server_url": "https://keycloak.corp.ru",
    "realm": "employees",
    "client_id": "vacation-app",
    "client_secret": "<из Keycloak>",
    "redirect_uri": "https://vacation.corp.ru/auth/callback",
    "scope": "openid email profile",
    "button_title": "Войти через Keycloak",
    "verify_tls": True,
}
```

Секрет клиента хранится в переменных окружения, а не в репозитории.

### 3.3. Что проверяется

- Подпись `id_token` сверяется с ключами realm (JWKS), ключи кэшируются.
  Без проверки подписи токен — просто строка, которую можно подделать.
- Проверяются издатель (`issuer`) и адресат (`audience`).
- Параметр `state` сверяется с сохранённым в сессии: это защита от
  подделки запроса.

## 4. Вход по паролю

Оставлен как запасной вариант для всех пользователей. Отключается
одной настройкой:

```python
SSO_ALLOW_PASSWORD_LOGIN = False
```

При отключении попытка входа по паролю возвращает понятный отказ,
а экран входа перестаёт показывать форму.

Рекомендация: не отключать до тех пор, пока доменный вход не проверен
на пилотной группе. Иначе сбой в домене заблокирует доступ всем,
включая администратора.

## 5. Диагностика

| Что видит пользователь | Вероятная причина |
|---|---|
| `provider_not_configured` | Способ выключен в настройках или не установлен `gssapi` |
| Браузер просит пароль вместо автоматического входа | Адрес не добавлен в доверенные в политиках браузера |
| `invalid_ticket` | Keytab не совпадает с принципалом, или расходятся часы сервера и контроллера домена |
| `employee_not_found` | Человек есть в домене, но не загружен в систему из кадровой выгрузки |
| `email_claim_missing` | В Keycloak не настроен маппер `email` |
| `state_mismatch` | Потеряна сессия между началом входа и возвратом; проверьте настройки cookie за прокси |

Проверить, какие способы видит клиент:

```bash
curl https://vacation.corp.ru/api/v1/auth/methods/
```
