# Первый администратор

> Часть комплекта проектной документации. Обзор и порядок чтения — в `README.md`.

После развёртывания в базе нет ни одного пользователя, а войти в систему
и загрузить сотрудников может только администратор. Чтобы не создавать его
вручную через консоль сервера, бэкенд при каждом старте контейнера выполняет
команду `ensure_admin`.

---

## 1. Как работает

1. Контейнер стартует, применяются миграции.
2. Выполняется `python manage.py ensure_admin`.
3. Запускается gunicorn.

Команда идемпотентна, поэтому безопасна при каждом перезапуске:

| Ситуация | Что происходит |
|---|---|
| `ADMIN_EMAIL` и `ADMIN_PASSWORD` не заданы | Ничего, сервис запускается |
| Задана только одна из двух переменных | Предупреждение в логе, администратор не создаётся, сервис запускается |
| Пользователя с такой почтой нет | Создаётся администратор |
| Пользователь с такой почтой уже есть | **Ничего не меняется** — ни пароль, ни права, ни имя |
| Пароль не прошёл проверку надёжности | Ошибка, контейнер не стартует |
| Табельный номер занят другим сотрудником | Ошибка, контейнер не стартует |
| Неверный формат `ADMIN_HIRE_DATE` | Ошибка, контейнер не стартует |

Почта сравнивается без учёта регистра: `Ivanov@Corp.ru` и `ivanov@corp.ru`
считаются одним пользователем.

Команда вызывается и при `RUN_MIGRATIONS=0`: в Kubernetes миграции идут
отдельным Job до старта реплик, а администратор всё равно нужен.

## 2. Переменные

| Переменная | Обязательна | По умолчанию | Описание |
|---|---|---|---|
| `ADMIN_EMAIL` | Да | — | Почта, она же логин |
| `ADMIN_PASSWORD` | Да | — | Пароль |
| `ADMIN_FULL_NAME` | Нет | `Администратор` | ФИО |
| `ADMIN_EMPLOYEE_NUMBER` | Нет | `ADMIN-0001` | Табельный номер, должен быть уникальным |
| `ADMIN_HIRE_DATE` | Нет | сегодня | Дата приёма, `ГГГГ-ММ-ДД` |

Последние три нужны, потому что у модели сотрудника эти поля обязательны.

Создаваемый пользователь получает все права: администратор приложения
(`is_admin`), доступ к админке Django (`is_staff`) и суперпользователь
(`is_superuser`).

## 3. Требования к паролю

Пароль проверяется теми же валидаторами Django, что и при обычной смене
пароля: не короче 8 символов, не только из цифр, не из списка
распространённых, не похож на почту и имя.

Слабый пароль останавливает запуск контейнера, а не создаёт уязвимую учётную
запись. Это сознательное решение: учётная запись администратора самая
привилегированная в системе и обычно доступна из интернета. Проверка
выполняется только при создании — если администратор уже есть, смена
`ADMIN_PASSWORD` ни на что не влияет.

## 4. Безопасность

**Пароль не выводится в лог** ни в одном сообщении, включая сообщения
об ошибках. В entrypoint не включена трассировка оболочки (`set -x`),
которая напечатала бы аргументы команд, — это зафиксировано тестом.

**Смена пароля через переменную не работает.** Это намеренно: иначе любой,
кто может изменить окружение сервиса, мог бы при перезапуске сбросить пароль
администратора. Пароль меняется в интерфейсе приложения или командой
`python manage.py changepassword <почта>`.

**После первого входа переменные обязательно удалить** — `ADMIN_PASSWORD`
и `ADMIN_EMAIL` (или файл `ADMIN_PASSWORD_FILE`). Администратор уже создан,
а пароль в окружении виден в дампах процессов, `docker inspect`, консоли
площадки — каждому, у кого есть к ней доступ. Шаг входит в чек-лист
запуска на любой площадке (раздел 5).

**Команда выполняется там же, где миграции.** При `RUN_MIGRATIONS=0`
(Kubernetes) её делает Job миграций, а веб-контейнеры её не вызывают —
пароль им не нужен и в их окружении его быть не должно.

**Пароль можно передать файлом** — `ADMIN_PASSWORD_FILE` (смонтированный
секрет); снимается только завершающий перевод строки.

**Пароль хранится в секретах площадки**, а не в репозитории: в `.env`
локально, в Variables на Railway, в Secret в Kubernetes.

## 5. Площадки

**Docker Compose.** Задать переменные в `.env` до первого `docker compose up`.
Если пароль содержит символ `$`, его нужно удвоить (`$$`): Compose
подставляет переменные в значения из `.env`.

**Railway.** Задать `ADMIN_EMAIL` и `ADMIN_PASSWORD` в Variables сервиса
бэкенда, перезапустить развёртывание.

**Kubernetes.** Отдельный Secret `vacation-admin` (образец — в
`deploy/k8s/secret.example.yaml`). Он подключён только к Job миграций,
в веб-подах пароля нет. Если Secret не создан, Job просто пропускает шаг.

**Чек-лист после первого входа (все площадки):**

1. Войти под администратором, убедиться, что вход работает.
2. Удалить пароль из окружения:
   - Docker Compose — убрать `ADMIN_PASSWORD` из `.env`;
   - Railway — удалить `ADMIN_EMAIL` и `ADMIN_PASSWORD` в Variables;
   - Kubernetes — `kubectl -n vacation delete secret vacation-admin`.
3. Сменить пароль в интерфейсе, если он передавался через чат, почту или
   тикет.

Если несколько реплик стартуют одновременно, администратора создаст первая,
остальные увидят его и ничего не изменят — одновременное создание
обрабатывается как штатная ситуация.

## 6. Вручную

Команду можно выполнить и в работающем контейнере:

```bash
docker compose exec backend python manage.py ensure_admin
```

Альтернатива без переменных окружения — штатная команда Django, которая
спросит поля интерактивно:

```bash
docker compose exec backend python manage.py createsuperuser
```
