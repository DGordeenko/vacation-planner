# Демонстрационный режим

> Часть комплекта проектной документации. Обзор и порядок чтения — в `README.md`.

Чтобы познакомиться с системой, не нужно готовить кадровую выгрузку,
календарь и правила. Достаточно нажать на экране входа кнопку
**«Демо-режим»** и выбрать роль: откроется вымышленная компания на 157 человек
с готовым графиком на следующий год. Пароль не нужен.

---

## 1. Как устроено

Демо работает **на том же экземпляре**, что и рабочая система, но
**в отдельной базе данных**. Справочники, праздники, правила, настройки
и брендирование в модели данных глобальные: в общей базе демо переписало бы
рабочие. Поэтому разделение сделано на уровне базы, а не отдельных таблиц.

```
Экран входа ── «Демо-режим» ── выбор роли ── POST /api/v1/auth/demo-login/
                                                    │
                                     токен демо-базы, схема Demo
                                                    │
      Запрос с заголовком «Authorization: Demo <токен>»
                                                    │
                          DemoDatabaseMiddleware: весь запрос — на демо-базе
```

| Что | Как |
|---|---|
| Какую базу использовать | Определяет заголовок авторизации. Схема `Demo` — демо-база, `Token` — рабочая |
| Подмена базы | На время запроса соединение `default` заменяется соединением `demo`. Подмена действует на весь код: запросы, транзакции, аудит |
| Проверка токена | Демо-токен ищется только в демо-базе, рабочий — только в рабочей. Подменой заголовка попасть в чужую базу нельзя |
| Права | Те же, что в рабочей системе. Администратор демо — администратор только демо-базы |
| Почта | Не отправляется: адреса вымышленные. Уведомления в ленте приложения есть |

Почему подмена соединения, а не маршрутизатор баз Django: `transaction.atomic()`
без явного указания базы открывает транзакцию в `default`. С маршрутизатором
запись уходила бы в демо-базу мимо транзакции, и откат, например пробного
импорта, переставал бы работать. Подмена соединения такого не допускает.

Отпуска вносятся через те же проверки, что при сохранении в интерфейсе,
а графики проходят штатную отправку и согласование. Поэтому на заполненном
графике соблюдены лимиты по тегам и нормы, а если правила поменяются,
демо покажет новое поведение, а не устаревшую картинку. Подбор
детерминирован: при каждой загрузке получается одно и то же.

## 4. Включение и сброс

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEMO_MODE_ENABLED` | `False` | Показывать кнопку демо и принимать вход в демо |
| `DEMO_DATABASE_URL` | SQLite во временном каталоге контейнера | Демо-база. Должна отличаться от `DATABASE_URL` |
| `DEMO_LOAD_ON_START` | `1` | Загружать демо-данные при старте контейнера |

При включённом демо контейнер при каждом старте применяет миграции
к демо-базе и **загружает данные заново** (`load_demo`, около 15 секунд).
Так демо само возвращается к исходному состоянию после посетителей.
Кнопка появляется на экране входа, только когда данные загружены.

Сбросить без перезапуска:

```bash
docker compose exec backend python manage.py load_demo
```

Команда очищает только демо-базу. Если `DEMO_DATABASE_URL` по ошибке указывает
на рабочую базу, команда откажется работать, а не сотрёт рабочие данные.

Чтобы сбрасывать демо регулярно, команду можно поставить в расписание
площадки (cron в Docker-хосте, CronJob в Kubernetes).

### Несколько реплик

Демо-база по умолчанию — файл внутри контейнера, у каждой реплики свой.
С одной репликой (Docker Compose, Railway) это то, что нужно. При нескольких
репликах посетитель, попав на другую, увидит другое состояние демо. Тогда:

1. Создать отдельную базу Postgres для демо и задать её в `DEMO_DATABASE_URL`.
2. Задать `DEMO_LOAD_ON_START=0`, чтобы реплики не перезагружали общую базу.
3. Выполнять `migrate --database=demo` и `load_demo` отдельным Job.

## 5. Безопасность

- Демо выключено по умолчанию. Если `DEMO_MODE_ENABLED` не задан, эндпоинт
  входа отвечает 404, а выданные ранее демо-токены перестают приниматься.
- Вход без пароля даёт права только в демо-базе. Рабочих сотрудников,
  графиков и настроек демо-посетитель не видит: это проверяется тестами
  изоляции в `backend/demo/tests.py`.
- Демо-администратор не получает доступа к админке Django: она работает
  на сессиях рабочей базы.
- В демо-данных нет реальных людей: имена вымышленные, почтовый домен
  `test-corp.example` зарезервирован для примеров.
- Интерфейс в демо постоянно показывает плашку «Демо-режим», чтобы данные
  не приняли за настоящие.

## 6. API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/auth/methods/` | Поле `demo`: `enabled` и список ролей `code`, `title`, `description`, `full_name` |
| POST | `/api/v1/auth/demo-login/` | Тело `{"role": "employee" \| "manager" \| "admin"}`. Ответ: `token`, `employee_id`, `scheme` (`Demo`), `role`. 400 — неизвестная роль, 404 — демо выключено, 503 — данные не загружены |

Дальнейшие запросы — с заголовком `Authorization: Demo <token>`.
