# Резервное копирование и восстановление

> Часть комплекта проектной документации. Обзор и порядок чтения — в `README.md`.

Вся ценность системы — в рабочей базе PostgreSQL: сотрудники, графики,
решения по согласованию, регистр начислений и списаний, журнал изменений.
Файлов пользователей приложение не хранит, поэтому копии базы достаточно,
чтобы восстановить систему целиком.

Демо-база в копию не входит: она перезаписывается при каждом старте.

---

## 1. Что и как копируется

| Площадка | Как | Расписание и хранение |
|---|---|---|
| Docker Compose | Сервис `backup`, скрипт `deploy/backup/pg-backup.sh` | Раз в сутки, 14 дней; настраивается |
| Kubernetes | Тот же скрипт в CronJob (раздел 3) | По расписанию CronJob |
| Railway | Встроенные снимки тома Postgres + выгрузка вне Railway (раздел 4) | Ежедневно 6 дней, еженедельно 27 дней, ежемесячно 89 дней |

Копия — `pg_dump` в сжатом формате custom (`.dump`). Его можно
восстановить в базу любой версии PostgreSQL не ниже исходной, целиком
или по отдельным таблицам.

**Сколько данных можно потерять.** При ежесуточной копии — изменения
за сутки. В кампанию планирования это внесённые, но не согласованные
отпуска: сотрудники внесут их снова. Если такой потери много, уменьшите
`BACKUP_INTERVAL_HOURS`. Копия базы на 500 сотрудников занимает
единицы мегабайт и снимается за секунды.

## 2. Docker Compose

Сервис `backup` запускается вместе с остальными (`docker compose up -d`):

- раз в `BACKUP_INTERVAL_HOURS` часов (по умолчанию 24) пишет
  копию `vacation-ГГГГММДД-ЧЧММСС.dump` в каталог `BACKUP_HOST_DIR` на хосте
  (по умолчанию `./backups`);
- первая копия создаётся сразу при старте сервиса;
- удаляет копии старше `BACKUP_KEEP_DAYS` дней (по умолчанию 14), но только
  после того, как новая копия создана успешно. Если `pg_dump` начал падать,
  старые копии не удаляются;
- недописанная копия (`.partial`) удаляется. Годными выглядят только
  целые файлы.

Журнал — `docker compose logs backup`. Строка «ОШИБКА: копия не создана» —
повод разбираться: пароль, доступность базы, место на диске.

**Каталог копий — на другом диске.** Копия на том же диске, что и база,
не спасёт от отказа диска. Укажите `BACKUP_HOST_DIR` на другом томе или
сетевом хранилище либо настройте их копирование средствами хоста.

Снять копию вне расписания, например перед обновлением:

```bash
docker compose run --rm -e BACKUP_ONCE=1 backup
```

## 3. Kubernetes

Манифесты появятся в релизе 1.2 (`tasks/00-skeleton.md`, итерация 3).
До этого — CronJob на том же скрипте. Скрипт кладётся в ConfigMap,
каталог копий — PersistentVolumeClaim на хранилище, отличном от тома базы.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: vacation-backup
spec:
  schedule: "15 2 * * *"          # 02:15 UTC ежедневно
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: postgres:16-alpine   # версия не ниже версии сервера
              command: ["/bin/sh", "/scripts/pg-backup.sh"]
              env:
                - { name: BACKUP_ONCE, value: "1" }
                - { name: BACKUP_KEEP_DAYS, value: "14" }
                - { name: PGHOST, value: postgres }
                - { name: PGDATABASE, value: vacation }
                - name: PGUSER
                  valueFrom: { secretKeyRef: { name: vacation-db, key: user } }
                - name: PGPASSWORD
                  valueFrom: { secretKeyRef: { name: vacation-db, key: password } }
              volumeMounts:
                - { name: scripts, mountPath: /scripts }
                - { name: backups, mountPath: /backups }
          volumes:
            - name: scripts
              configMap: { name: vacation-backup-script }
            - name: backups
              persistentVolumeClaim: { claimName: vacation-backups }
```

```bash
kubectl create configmap vacation-backup-script --from-file=deploy/backup/pg-backup.sh
```

Если база — управляемый сервис облака, у него есть собственные снимки.
Включите их, а CronJob оставьте для копии, которая не зависит от провайдера.

## 4. Railway

**Встроенные снимки.** В сервисе Postgres: вкладка **Backups** → включить
расписания. Рекомендуется включить все три:

| Расписание | Хранится |
|---|---|
| Ежедневно | 6 дней |
| Еженедельно | 27 дней |
| Ежемесячно | 89 дней |

Снимок можно снять и вручную, кнопкой на той же вкладке (лимит — половина
размера тома). Снимите его перед обновлением, перед загрузкой кадровой
выгрузки и перед открытием кампании.

Ограничения встроенных снимков (документация Railway, раздел Volumes →
Backups):

- восстановить можно только в тот же проект и окружение;
- удаление тома удаляет и все его снимки;
- функция помечена как развивающаяся.

**Поэтому нужна и копия вне Railway.** Раз в неделю и перед важными шагами
снимайте её с рабочего компьютера администратора. Адрес базы — переменная
`DATABASE_PUBLIC_URL` сервиса Postgres (вкладка Variables).

```bash
pg_dump --format=custom --no-owner \
  --file="vacation-$(date +%Y%m%d).dump" "$DATABASE_PUBLIC_URL"
```

Версия `pg_dump` на компьютере должна быть не ниже версии Postgres
на Railway — её показывает `SELECT version();`. Файл копии содержит
данные всех сотрудников: храните его там же, где кадровые документы.

**Восстановление встроенного снимка.**

1. Вкладка Backups → нужная дата → **Restore**.
2. Railway подготовит изменение: новый том с датой снимка подключается
   вместо текущего. Старый том сохраняется отключённым.
3. Проверьте изменение (Details на схеме проекта) и нажмите **Deploy**.

## 5. Восстановление из файла `.dump`

Восстановление заменяет текущие данные: всё, что внесли после копии,
пропадёт. Перед восстановлением снимите копию текущего состояния — на случай,
если ошиблись файлом.

1. **Остановить приложение,** чтобы во время восстановления никто ничего
   не записал: `docker compose stop backend frontend`. В Kubernetes —
   масштабировать бэкенд до 0, на Railway — остановить сервис бэкенда.
2. **Восстановить** одной транзакцией. При ошибке база останется как была:

   ```bash
   # Docker Compose: файл из ./backups виден в контейнере backup как /backups
   docker compose run --rm --entrypoint sh backup -c \
     'pg_restore --clean --if-exists --no-owner --single-transaction \
        -d "$PGDATABASE" /backups/vacation-20270115-021500.dump'

   # Railway или любая база по адресу
   pg_restore --clean --if-exists --no-owner --single-transaction \
     -d "$DATABASE_PUBLIC_URL" vacation-20270115.dump
   ```
3. **Запустить приложение.** Миграции при старте доведут схему до текущей
   версии кода, если копия была снята на более старой версии.
4. **Проверить:** вход администратора, число сотрудников в разделе
   «Сотрудники», график любого сотрудника.

## 6. Проверка копий

Копия, которую ни разу не восстанавливали, — не копия. Раз в квартал и
перед открытием кампании восстановите свежую копию в **отдельную** базу
и сверьте число сотрудников:

```bash
createdb restore_check
pg_restore --no-owner -d restore_check vacation-20270115-021500.dump
psql -d restore_check -c "select count(*) from employees_employee"
dropdb restore_check
```

Так скрипт проверен при разработке: копия базы на 157 сотрудников
восстановлена в отдельную базу, а также поверх рабочей с `--clean`;
число сотрудников и записей регистра начислений совпало с исходной.
