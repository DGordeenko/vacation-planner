# Развёртывание на Railway

> Часть комплекта проектной документации. Обзор и порядок чтения — в `README.md`.

Railway — одна из трёх поддерживаемых площадок, наряду с Docker
и Kubernetes. Образы те же, что и для Docker: Railway собирает их
из `backend/Dockerfile` и `frontend/Dockerfile`.

---

## 1. Схема

```
Браузер ──https──▶ frontend (публичный домен, nginx)
                      ├─ /         → SPA
                      └─ /api/, /static/ ──private network──▶ backend:8000 ──▶ Postgres
```

Сотрудники видят один домен — домен фронтенда. Запросы к API nginx
проксирует на бэкенд по внутренней сети Railway. Так не нужны ни CORS,
ни второй публичный домен, ни сборка фронтенда с адресом API.

Бэкенду публичный домен не нужен. Исключение — админка Django:
она работает через тот же прокси, по адресу `https://<домен фронтенда>/admin/`.

## 2. Сервисы

Проект Railway из репозитория, три сервиса:

| Сервис | Источник | Root Directory |
|---|---|---|
| `backend` | GitHub-репозиторий | `backend` |
| `frontend` | GitHub-репозиторий | `frontend` |
| `Postgres` | Шаблон PostgreSQL | — |

Имя сервиса бэкенда входит во внутренний адрес
(`backend.railway.internal`). Если назвать сервис иначе, поправьте
`BACKEND_URL` ниже.

## 3. Переменные

**backend** (Variables):

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` — ссылка на переменную сервиса Postgres |
| `SECRET_KEY` | Случайная строка от 50 символов. Не менять после запуска: выданные токены входа перестанут действовать |
| `ALLOWED_HOSTS` | `<домен фронтенда>,healthcheck.railway.app` — см. ниже |
| `CSRF_TRUSTED_ORIGINS` | `https://<домен фронтенда>` — нужно для входа в админку Django |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Первый администратор (`14-initial-admin.md`). После первого входа можно удалить |
| `DEMO_MODE_ENABLED` | Не задавать на рабочем стенде (`15-demo-mode.md`) |

Почему в `ALLOWED_HOSTS` домен фронтенда, а не бэкенда: nginx передаёт
бэкенду заголовок `Host` исходного запроса, то есть домен фронтенда.
`healthcheck.railway.app` — адрес, с которого Railway проверяет готовность
нового развёртывания (документация Railway, Deployments → Healthchecks).
Если адреса нет в списке, проверка получает 400, и развёртывание не проходит.

**frontend** (Variables):

| Переменная | Значение |
|---|---|
| `BACKEND_URL` | `http://backend.railway.internal:8000` — без пути и без «/» в конце |
| `PORT` | `8080` (порт nginx в образе) |

`VITE_API_BASE_URL` не задавать: при пустом значении интерфейс обращается
к API относительным путём, через прокси.

## 4. Настройки сервисов

**backend:**
- Settings → Deploy → Healthcheck Path: `/api/health/`.
- Settings → Networking: публичный домен не нужен. Порт для внутренней
  сети — 8000, его слушает gunicorn.
- Реплика одна. Миграции применяются при старте контейнера, и при нескольких
  репликах они конкурировали бы (`README.md`, раздел про Kubernetes).

**frontend:**
- Settings → Networking → Generate Domain (или свой домен), порт 8080.
- Healthcheck Path: `/`.

**Postgres:** вкладка Backups — включить расписания (`16-backups.md`, раздел 4).

## 5. Проверка после развёртывания

1. `https://<домен фронтенда>/api/health/` — ответ `{"status": "ok", ...}`.
2. Вход администратора, раздел «Сотрудники» открывается.
3. Пересоберите только бэкенд (Redeploy) и, не трогая фронтенд, снова
   откройте `/api/health/`. Ответ должен прийти: nginx переразрешает
   адрес бэкенда, а не запоминает старый IP (PR #13).
4. Ссылка-приглашение из раздела «Сотрудники» открывает экран задания пароля.

## 6. Вариант с двумя доменами

Если фронтенд и бэкенд должны жить на разных публичных доменах, например
API нужен внешней системе:

- у бэкенда сгенерировать домен; в `ALLOWED_HOSTS` — домен бэкенда
  и `healthcheck.railway.app`;
- в `CORS_ALLOWED_ORIGINS` и `CSRF_TRUSTED_ORIGINS` — `https://<домен фронтенда>`;
- фронтенду задать `VITE_API_BASE_URL=https://<домен бэкенда>`. Переменная
  нужна на этапе сборки: Railway передаёт переменные сервиса в сборку
  Dockerfile как аргументы, если они объявлены через `ARG`, а в
  `frontend/Dockerfile` это так. После изменения нужна пересборка.

Основной вариант (раздел 1) проще: один домен и меньше настроек, которые
легко рассинхронизировать.

## 7. Чего пока нет

- **Почтовая очередь по расписанию.** Образ бэкенда всегда запускает
  gunicorn: команду для cron-сервиса Railway через него сейчас не выполнить.
  Пока почта не включена (`MAIL_NOTIFICATIONS_ENABLED` не задана),
  это не мешает. Расписание почты на всех трёх площадках — релиз 1.2.
- Регламент обновления: перед Redeploy с новыми миграциями снимите снимок
  базы вручную (`16-backups.md`, раздел 4).
