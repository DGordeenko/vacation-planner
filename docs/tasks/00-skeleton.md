## Решение по адресации API

Клиент обращается к API по относительному пути `/api/v1`. В разработке это
работает через прокси в `vite.config.ts`, в продакшене прокси нет.

Принято: **nginx во фронтенд-контейнере проксирует `/api` на бэкенд**,
а переменная `VITE_API_BASE_URL` поддерживается как переопределение.
Пустая переменная — относительный путь и проксирование (Docker, Kubernetes);
заданная — абсолютный адрес бэкенда (Railway, где сервисы получают разные
домены). Один образ подходит ко всем трём сценариям.

## Итерация 1. Локальный запуск через Docker

Минимум, после которого проект поднимается одной командой.

### Backend

- **База через `DATABASE_URL`.** Сейчас в `settings.py` жёстко прописан SQLite,
  переменная не читается. Подключить разбор `DATABASE_URL` с запасным
  значением на SQLite для локального прогона тестов.
- **Статика:** задать `STATIC_ROOT`, подключить WhiteNoise. Без этого админка
  Django приедет без оформления.
- **Сервер приложений:** gunicorn, порт из `PORT`.
- **`GET /api/health/`** — публичный эндпоинт, проверяет доступность базы.
  Возвращает понятный статус при недоступной БД, а не падает с 500.
  Тест на оба случая.
- **Entrypoint:** применение миграций при старте контейнера.
  *(В Kubernetes это переедет в отдельный шаг — см. итерацию 3.)*

### Frontend

- `VITE_API_BASE_URL` как переопределение базового адреса (см. решение выше).
- Production-сборка отдаётся nginx на порту из `PORT`, `/api` проксируется
  на бэкенд.

### Контейнеры

- Многоэтапные Dockerfile для `backend/` и `frontend/`, каждый собирается
  из своей папки.
- `docker-compose.yml`: backend, frontend, postgres. Healthcheck на
  `/api/health/`.
- Образы переносимые: порт и настройки только из переменных окружения,
  привязки к конкретному провайдеру в коде нет.

### Готовность итерации 1

1. `docker compose up` поднимает три сервиса.
2. Фронтенд открывается и работает с бэкендом.
3. `GET /api/health/` отвечает и подтверждает связь с базой.
4. Все 269 тестов проходят.
5. Секретов в репозитории нет, `.env` в `.gitignore`.

## Итерация 3. Kubernetes и Railway

- ~~**Kubernetes:**~~ сделано — `deploy/k8s/`, `docs/18-deploy-kubernetes.md`. Манифесты или Helm-чарт — Deployment на сервис, Service,
  Ingress, Secret и ConfigMap, пробы liveness и readiness на `/api/health/`.
  **Миграции вынести из entrypoint** в Job или initContainer: при нескольких
  репликах одновременный старт миграций приводит к конкуренции.
  CronJob для почтовой очереди (`send_mail_queue`, см. `docs/12-mail-setup.md`).
- **Railway:** по сервису на папку, PostgreSQL плагином (даёт `DATABASE_URL`),
  healthcheck на `/api/health/`, `VITE_API_BASE_URL` с адресом бэкенда,
  `CORS_ALLOWED_ORIGINS` и `CSRF_TRUSTED_ORIGINS` с доменом фронтенда.
  Почтовая очередь на их cron.
- Короткая инструкция по развёртыванию в `docs/`.

## Ограничения для всех итераций

- Бизнес-логику, модели и правила проверки не менять. Исключение — правки,
  прямо необходимые для запуска; каждая объясняется в теле коммита.
- Библиотеки только в рамках `docs/02-adr-002-stack.md` и уже согласованных
  исключений в `backend/requirements.txt`. Новая библиотека — через вопрос.
- Секреты не коммитить; в репозитории только `.env.example` с безопасными
  значениями.
- При неясности или противоречии в документах — остановиться и спросить.
