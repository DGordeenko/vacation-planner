**Результат:** Pull Request в `main`
**Бизнес-логики на этом этапе нет.**

## Прежде чем начинать

1. Прочитать `docs/` целиком, начиная с `docs/README.md`.
2. **Разрешить противоречие №1 из `docs/README.md`.** Вне репозитория
   существует работающая реализация с 269 проходящими тестами. Это задание
   написано так, будто код пишется с нуля. Нужно подтверждение владельца
   проекта: переносим существующий код или пишем заново. **До ответа
   не начинать.**

### Приложения бэкенда

Создать пустыми, по модулям из ADR-001 (`docs/01-adr-001-architecture.md`):

| Приложение | Модуль |
|---|---|
| `employees` | Сотрудники, оргструктура, роли, теги и лимиты |
| `company` | Календарь праздников, настройки компании, брендирование |
| `schedule` | График, правила проверки, регистры, согласование, уведомления |
| `audit` | Журнал изменений |

Модули «Уведомления» и «Теги» из ADR-001 не выделяются в отдельные приложения:
уведомления неотделимы от событий графика, теги — от сотрудников. Отдельные
приложения создали бы круговые зависимости между модулями.

Приложения `sso` (доменная аутентификация) и `mailer` (почтовые уведомления)
на этом этапе **не создаются**: они за границами релиза 1.

Модели не описывать — только каркас приложений. Исключение — модель
пользователя, см. ниже.

## Backend

- Настройки через переменные окружения: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`,
  `DATABASE_URL`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS`, `PORT`.
- **Пользовательская модель — до первой миграции.** Это единственная модель
  этапа: `employees.Employee` с минимальным набором полей
  (`employee_number`, `full_name`, `email`, `hire_date`), email как
  идентификатор для входа. Менять модель пользователя после первой миграции
  в Django крайне болезненно, поэтому она создаётся сразу.
- `GET /api/health/` — проверка связи, включая доступность базы данных.
  Эндпоинт публичный.
- Запуск через gunicorn, статика через WhiteNoise, порт из `PORT`.
- Автоприменение миграций при старте контейнера.
- pytest + pytest-django, тест на `/api/health/` (успех и поведение при
  недоступной базе).
- ruff как линтер.

## Frontend

- Одна страница: показывает статус связи с бэкендом через `/api/health/`.
  Три состояния — проверяем, доступен, недоступен.
- Адрес API из переменной окружения (`VITE_API_BASE_URL`).
- Production-сборка отдаётся nginx на порту из `PORT`.
- ESLint, `npm run build` без ошибок типов.

Оформление на этом этапе минимальное. Дизайн-решения из
`docs/06-ux-branding.md` применяются начиная с этапа, где появляется интерфейс.

## Контейнеры

Многоэтапные Dockerfile для `backend/` и `frontend/`, каждый сервис собирается
из своей папки.

Образы должны оставаться переносимыми: порт берётся из `PORT`, настройки —
из переменных окружения, привязки к конкретному хостинг-провайдеру в коде нет.
Площадка размещения не выбрана (`docs/02-adr-002-stack.md`, разд. 5), и такой
контейнер запускается и на своём сервере, и у любого облачного провайдера.

## CI

`.github/workflows/ci.yml`, на push и pull request: `pytest`, `ruff check`,
`npm run lint`, `npm run build`.

## Журналируемость

- Небольшие коммиты `тип: описание на русском`, в теле — зачем.
- В конце — Pull Request в `main`: что сделано, как проверить, какие решения
  приняты и почему. Описание понятно не-разработчику.
- `CHANGELOG.md` с записью об этапе 0.

## Ограничения

- Никакой бизнес-логики, ролей, правил проверки и сущностей из модели данных.
  Единственная модель — пользователь (см. выше).
- Библиотеки только в рамках `docs/02-adr-002-stack.md`. Исключения,
  необходимые для этого этапа: `gunicorn`, `whitenoise`, `psycopg`,
  `dj-database-url` (разбор `DATABASE_URL`), `pytest`, `pytest-django`, `ruff`.
  Любая библиотека сверх этого списка — через вопрос.
- Секреты не коммитить, `.env` в `.gitignore`, в репозитории только
  `.env.example` с безопасными значениями.
- При неясности или противоречии в документах — остановиться и спросить.

## Критерии готовности

1. `docker compose up` поднимает backend, frontend и postgres.
2. Фронтенд показывает, что бэкенд доступен.
3. `GET /api/health/` отвечает и подтверждает связь с базой.
4. Тесты и линтеры проходят локально, CI зелёный.
5. Pull Request создан, описание понятно человеку без опыта разработки.
6. В репозитории нет ни одного секрета.
